# 示例：AI Agent 产品竞品调研

## 用户可能的请求

```text
我想调研几个 AI Agent 产品，比如 Manus、Genspark、ChatGPT Agent、Claude、通义千问等，看看它们在任务规划、工具调用和用户体验上有什么差异。
```

## 应触发的处理方式

1. 确认调研用途：产品规划、功能优先级、Agent 体验设计、汇报材料或真实任务测试。
2. 默认先做公开资料、功能矩阵和公开口碑分析。
3. 不直接评价任务完成质量，除非用户提供真实任务测试材料。
4. 若用户需要真实任务对比，进入可选 case 测试模块，并共同设计任务集。

## 可能的功能矩阵维度

| 维度 | 说明 |
|---|---|
| 任务规划 | 是否展示计划、是否可调整计划 |
| 工具调用 | 浏览器、代码、文件、表格、图片、API 等 |
| 过程透明 | 是否显示中间步骤、来源和决策依据 |
| 用户控制 | 是否能暂停、修改、接管、回滚 |
| 异常恢复 | 失败后是否能重试、解释、换路径 |
| 长程执行 | 是否支持多步骤长任务、后台运行 |
| 结果交付 | 是否生成文档、表格、网页、文件等成品 |
| 多轮修正 | 是否能根据反馈迭代结果 |
| 权限与安全 | 是否清楚告知外部操作、数据访问和风险 |
| 成本/时长 | 是否显示预计耗时、消耗或限制 |

## 公开体验反馈分析方向

| 主题 | 可观察材料 |
|---|---|
| 任务完成感 | 用户是否觉得真的完成了任务而非只给建议 |
| 过程可控感 | 是否吐槽黑箱、不可控、乱点工具 |
| 稳定性 | 是否常失败、卡住、循环、跑偏 |
| 结果可用度 | 输出是否能直接交付或还需大量人工修改 |
| 学习成本 | 用户是否理解该如何下任务 |
| 权限焦虑 | 用户是否担心隐私、误操作、外部发布 |
| 差异化心智 | 用户是否把产品视为“办事助手”而非聊天机器人 |

## 可能的调研结论形式

```text
事实依据：竞品在工具调用、长程执行、浏览器操作和结果交付上形成不同产品形态。
公开观察：用户对 Agent 的评价常集中在“能否真的完成任务”“过程是否可控”“失败后是否能恢复”。
分析判断：Agent 产品竞争不只是工具数量，而是任务规划、过程透明、异常恢复、用户控制和交付物质量共同决定体验。
取长：若规划 Agent 能力，应优先明确目标任务边界和用户控制机制，避免只展示自动化能力而缺少可控感。
补短：{{竞品共同没做好的，有机会超越}}
避坑：{{竞品失败/收缩路径，要规避}}
待验证点：具体任务完成质量必须通过统一任务集和人工测试验证。
```

## 如进入 case 测试

先共同确认任务类型，例如：

- 搜集资料并输出报告；
- 制作表格或清单；
- 规划旅行或采购；
- 操作网页完成流程；
- 分析文件并生成结论；
- 多轮修改交付物。

测试任务应先作为草案，确认任务难度、输入材料、成功标准和记录模板后再执行。
