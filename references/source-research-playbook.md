# 真实联网检索与来源整理 Playbook

该文件定义 AI 产品竞品调研中的资料收集硬规则。AI 产品变化快，凡是用户要求生成报告、完成调研、整理近期动作、分析功能现状或用户口碑，必须先做真实联网检索或读取用户提供的最新资料，不能只凭模型记忆和模板生成内容。

## 硬规则

### 检索前必读（禁止现场试错已知失败通道）

检索前**必须先读** `references/sources-registry.md` 的可达性表和 `web-search-channels-in-this-env` memory，只使用已验证 ✅ 的通道。**禁止在每轮调研里重新试错已知 ❌ 的通道**——这是检索低效的主要来源（真实跑里百度/搜狗微信/Bing/36kr/量子位/Reddit 全试了一遍全失败，6+ 次死调用浪费）。

已验证 ✅ 通道（2026-07-09 复核确认）：

- 官方博客 sitemap.xml + 单篇直抓（seed/openai/anthropic/blog.google 等）。注意：博客**列表页**多为 SPA（seed.bytedance.com/zh/blog、openai.com/news/product-releases），curl 拿不到文章列表 → 改抓同站 `sitemap.xml` 取 `<loc>`+`<lastmod>`，再直抓单篇博文（单篇通常服务端渲染可读）。
- 服务端渲染官方页直抓：Anthropic `/news`、Google blog、TechCrunch、HuggingFace org/模型页（开源模型矩阵 + lastModified 当日期）
- HuggingFace org/模型页（开源模型矩阵 + lastModified 当日期）；部分模型卡需认证（401），改取 org 页时间戳或同 org 公开模型卡
- Bing `www.bing.com` + cookie jar（`-c jar -b jar`，无 cookie 会 SSL exit 35；完整配方见 sources-registry.md）。中文产品词被 SEO 镜像站污染，英文/混合查询更稳
- TechCrunch `?s=` 搜索（英文媒体；搜索结果按相关性而非时间，需手动挑窗口内文章）
- 公众号全文 `mp.weixin.qq.com/s/...`（用户贴 URL 时直读 `js_content`）

已验证 ❌ 通道（禁止现场重试）：百度（curl 返回 ~1.5KB 反爬挑战页）、搜狗微信（连发触发验证码）、cn.bing.com（SSL exit 35）、36kr、量子位、Reddit RSS、内置 WebSearch、小红书/知乎/微博全文（反爬）。

> 注：www.bing.com + cookie jar 是 ✅，与 cn.bing.com（❌）区分。百度/搜狗微信在本机已不可用，不要现场重试。

### 检索机制（不依赖其他 skill）

本 skill 自带检索能力，**不调用 web-access 或任何其他 skill**。检索顺序：**先直抓官方源 → TechCrunch/HF 补 → 用户补料（社媒口碑）**。

1. **先 curl 官方源**（最高优先级）：从 sources-registry 查产品的官方博客/changelog/新闻页 URL，用 sitemap.xml 的 lastmod 定位近期文章，直抓全文。这一步通常胜过十次泛搜。
2. **模型矩阵/发布日期** → HuggingFace org/模型页（开源厂商）+ 官方博客。
3. **媒体报道** → TechCrunch `?s=` 搜索（英文媒体）；中文媒体 36kr/量子位反爬不可用。
4. **应用商店信息** → iTunes Search API（版本/更新说明/功能现状，**不作为口碑依据**）。**对中文产品这是场景化/运营功能（高考、购物助手、课堂、博物馆讲解等）的一级通道**——这类功能发在 App Store 更新说明与公众号，不在技术博客/HF；技术博客抓不到时务必先查 iTunes Search API（`term=<产品拼音>&country=cn&entity=software`，中文 term 会 400，用拼音/英文）。解析 JSON 的 `releaseNotes` + `version` + `currentVersionReleaseDate`。
5. **公众号文章** → 用户贴 URL 时 curl 全文，正文在 `<div id="js_content">`，标题在 `var msg_title`。不依赖百度/搜狗微信发现 URL。
6. **社媒口碑**（知乎/微博/小红书真实评价+截图）→ curl 反爬抓不到，**必须向用户索要**（链接/截图/评论文本）。用户未提供时口碑章节输出缺口，不用应用商店评分凑。详见 `public-feedback-analysis.md`。

环境既无内置联网、又无 curl 时：**如实声明限制并停下**，输出框架/检索计划/待验证假设，不硬编结论。把限制写进过程 markdown。

**禁止行为：**

- 禁止调用 web-access、agent-browser、just-scrape、deep-research 等其他 skill 完成检索。
- 禁止现场重试已验证 ❌ 的通道（百度/搜狗/Bing/36kr/量子位/Reddit）。
- 禁止用模型记忆替代真实检索结果。
- 禁止把"我搜不到"包装成"竞品没有"。
- 禁止只读搜索结果 snippet 就下结论；必须 fetch 全文（见下"深读规则"）。
- 禁止用应用商店评分替代社媒口碑。

### 深读规则（不是浅搜）

模型检索信息少/不新/不准的主要原因是只读 snippet 不读全文。强制：

- 每个 query 拿到结果后，**必须 curl/WebFetch 排名前 2-3 的结果页全文**，从全文里提取动作、日期、细节，不是只看搜索摘要。
- 近期动作的**发布日期必须从原文里抓**，搜不到日期的进不了近期动作表。
- 官方博客/新闻页直接抓全文列表，逐篇看标题+日期，挑时间窗内的读正文。
- 公众号文章必须读 `js_content` 正文，不靠搜索摘要判断内容。

### 检索效率规则

- **每竞品固定少量高产出 query**，默认上限 4-5 条：官方博客/changelog直抓 / 公众号搜索 / 应用商店页面 / 一条社媒或媒体反馈。不要为单个竞品漫搜十几次。
- **先官方后社媒**。官方页一条 curl 常常胜过十条泛搜。
- **批量并行**：多竞品的 query 用并行 curl 一次发出，不要串行等待。
- **去重**：同一信息点多个来源只保留最权威一条，不重复记。
- **够用即停**：达到门禁阈值（默认 3 来源/2 类型）且能支撑核心章节即停，不为凑数继续搜。
- **记录每条 query**：过程 markdown 的检索记录表写清搜索词、平台、时间、结果，便于复盘为什么没搜到。

### 必须联网检索的情况

用户提出以下任一目标时，必须执行真实资料收集流程：

- 生成竞品调研报告；
- 完成某类 AI 产品竞品调研；
- 看“最近 / 近期 / 最新”动作；
- 整理产品功能现状；
- 分析市场用户口碑；
- 比较竞品当前能力；
- 输出可交付 Markdown / 飞书报告；
- 形成产品规划、prompt 优化、功能优先级判断所需结论。

这些场景下，不要先输出完整报告框架后结束；必须先收集资料、建立来源表，再生成结论。

### 可以不联网检索的情况

仅当用户明确只需要以下内容时，可以不检索：

- 调研框架；
- 调研方案；
- 报告模板；
- case 测试设计；
- 分析方法；
- 已有材料的整理和归纳。

如果用户说“先给我框架”“只要模板”“先设计流程”，则不需要联网。

### 无法联网时的处理

如果当前环境无法联网、搜索失败、目标平台不可访问，必须明确说明限制：

```text
当前无法完成最新资料验证。我可以先输出调研框架、资料收集清单或待验证假设，但不能把它写成已完成的最新竞品调研结论。
```

不要用模型记忆替代最新检索。

## 门禁文件与硬停规则

报告/调研执行模式下，模型必须维护两个文件供 `research-gate.js` 校验。这两个文件是门禁的依据，不是可选记录。

### research-state.md

范围与参数状态文件，模板见 `scripts/research-state-template.md`。关键字段：

- `范围已确认: yes/no` —— 用户明确确认范围前保持 no；置 yes 后才允许检索。脚本 `node scripts/research-gate.js scope` 据此放行。
- `来源阈值: N/M` —— 每竞品至少 N 条来源、M 种类型，默认 3/2，用户当次可调。脚本据此放行来源门禁。默认 2 类而非 3 类——中文竞品第 3 类"中文媒体/社媒"在本机常因百度反爬、Bing SEO 污染、公众号需 URL 直达而难以稳定获取；海外竞品通常可达 3/3，需更严时显式 `--min-types 3`。

### source-table.md

真实来源表。**脚本按列解析：第 1 列为竞品、第 3 列为来源类型**，因此表头列顺序必须固定为下表，不得调换：

| 竞品 | 信息点 | 类型 | 来源标题 | URL | 发布时间/访问时间 | 可信度 | 摘要 | 用于章节 |
|---|---|---|---|---|---|---|---|---|

`类型` 使用以下标准化取值，便于脚本统计覆盖类型数（"待验证"不计入类型覆盖）：

- 官方页面 / 官方更新日志 / 帮助文档 / 应用商店 / 媒体报道 / 社媒社区 / 用户反馈 / 用户提供 / 待验证

每条来源一行，真实检索到才写，不编造 URL。

### 来源不足硬停

检索后、写报告正文前，必须跑 `node scripts/research-gate.js sources`：

- **未通过 → 只能输出缺口报告（见 `references/gap-report.md`），停下。** 不得写报告正文、近期动作结论、功能现状或口碑结论，不得用"启示/建议/规划方向"凑篇幅。
- 通过 → 输出来源覆盖小结，可进入报告正文。

即使能跑通门禁，若某关键信息类型完全空白（如某竞品社媒反馈零可引用样本），在报告"资料来源与覆盖说明"中如实标注，不写成已覆盖。

## 资料收集流程

```text
1. 确认调研主题、竞品、时间范围和输出目标
2. 制定检索计划
3. 对每个竞品执行多来源检索
4. 记录来源表
5. 去重、分级、处理冲突
6. 生成近期动作表、功能矩阵、公开口碑矩阵
7. 基于来源表写报告和结论
```

## 最小来源覆盖要求

对每个核心竞品，至少尝试覆盖以下来源类型。无法覆盖时在来源覆盖说明中标注。

| 来源类型 | 目的 | 优先级 |
|---|---|---|
| 官方官网 / 产品页 | 产品定位、当前功能、入口形态 | 高 |
| 官方博客 / 更新日志 / 发布公告 | 近期动作、版本变化、能力发布 | 高 |
| 帮助中心 / 文档 / FAQ | 功能限制、使用方式、会员权限 | 高 |
| 应用商店 / App 页面 | 用户可见功能、版本更新、评分评论 | 中高 |
| 主流媒体 / 科技媒体 | 事件背景、行业解读、横向报道 | 中 |
| 社媒 / 社区 / 论坛 | 用户口碑、传播点、真实吐槽 | 中 |
| 用户截图 / 视频演示 | 实际界面、入口和使用路径 | 中 |
| 模型/API 文档 | 模型层能力、工具调用、多模态、上下文 | 视主题而定 |

## 来源表

所有用于报告的事实和重要判断都应能回到来源表。该表即门禁脚本读取的 `source-table.md`，**列顺序固定**（脚本按第 1 列竞品、第 3 列类型解析）：

| 竞品 | 信息点 | 类型 | 来源标题 | URL | 发布时间/访问时间 | 可信度 | 摘要 | 用于章节 |
|---|---|---|---|---|---|---|---|---|

### 类型（标准化取值）

- 官方页面
- 官方更新日志
- 帮助文档
- 应用商店
- 媒体报道
- 社媒社区
- 用户反馈
- 用户提供
- 待验证（不计入门禁类型覆盖）

## 可信度分级

| 可信度 | 标准 | 使用方式 |
|---|---|---|
| 高 | 官方页面、官方文档、更新日志、产品内截图、明确日期来源 | 可作为功能事实或近期动作依据 |
| 中 | 主流媒体报道、多篇独立报道互相印证 | 可作为背景或行业解读 |
| 中低 | 社媒用户反馈、社区讨论、应用商店评论 | 可作为公开口碑和市场感知依据 |
| 低 | 单条评论、未标明时间截图、二手转载、营销号总结 | 只能作为线索或待验证点 |

## 新鲜度规则

- 近期动作必须记录发布时间；若无发布时间，至少记录访问时间并标注时间不明。
- 超出用户指定时间范围的信息不得放入“近期动作总览”，只能作为背景。
- 时间不明的信息不能写成近期动作，只能写成“功能现状待验证”或“线索”。
- AI 产品变化快，报告中应写明检索时间。

## 去重与冲突处理

- 同一功能被多个来源报道时，合并为一个信息点，并保留最权威来源。
- 官方与媒体冲突时，以官方为准；媒体说法可作为补充或待验证。
- 官方宣传与用户反馈冲突时，分别写为“官方宣称”和“公开反馈”，不要直接判定谁对谁错。
- 无法确认的信息标注“待验证”，不得写成事实。
- 不要为了表格完整而补齐没有来源的内容。

## 近期动作整理规则

近期动作表必须从来源表生成。每条近期动作至少包含：

- 竞品；
- 动作；
- 类型；
- 时间；
- 来源；
- 对本次调研主题的影响；
- 待验证点。

没有来源或时间的信息不得进入近期动作表。

## 功能矩阵整理规则

功能矩阵也必须基于来源表或用户提供材料。

单元格建议写法：

```text
支持：{{形态/入口/限制}}（来源）
不支持：{{来源或原因}}
公开资料不明确
需人工验证
```

不要写“强 / 弱 / 好 / 差”这类真实体验判断，除非有公开反馈或测试材料支持。

## 用户口碑检索规则

如果用户要求口碑分析，必须明确采样平台和采样时间。

建议流程：

```text
1. 确定平台：小红书、微博、知乎、B站、应用商店、酷安、社区等
2. 每个平台记录搜索词和时间
3. 尽量收集正向、负向和中性反馈
4. 保留用户原话或截图摘要
5. 标注样本偏差和置信度
6. 聚类成体验主题
```

没有真实评论材料时，只能输出口碑采样计划，不要生成口碑结论。

## 输出前检查

生成报告前检查：

- 是否真的做了联网检索或读取用户最新资料？
