# 可选深度 Case 测试模块

该模块用于需要真实体验验证、回答策略对比、交互质量对比或 prompt/产品策略优化依据的场景。默认竞品调研不进入该模块。

## 进入条件

只有当用户明确表达以下需求时进入：

- 比较多个 AI 产品在同一任务下的回答策略。
- 验证公开口碑是否符合真实体验。
- 为 prompt、SP、交互策略或产品规划收集具体证据。
- 分析回答质量、交互体验、多轮表现、工具调用或任务完成效果。
- 用户明确说“设计测试 case”“做真实体验测试”“比较回答策略”等。

## 不进入条件

以下情况不要进入 case 测试：

- 用户只需要近期动作、功能矩阵或公开用户口碑。
- 用户只是要汇报材料或市场扫描。
- 用户没有时间、账号、权限或材料进行真实测试。
- 公开资料已经足够支持当前决策。

如果不进入，在报告中说明：

```text
本报告未包含统一真实 case 测试；体验判断主要来自公开用户反馈、媒体/社区材料和用户提供资料。
```

## 核心原则

1. **case 测试是调研设计，不是自动生成任务。** 测什么会决定最终能得出什么策略结论。
2. **不得直接定稿测试集。** 只能先输出草案，让用户确认、删除、替换、补充。
3. **不得直接定稿记录模板。** 提供轻量、标准、深度、自定义选项，让用户选择或修改。
4. **策略维度从材料中生成。** 不固定套用历史项目维度。
5. **没有真实回填材料时，不写真实体验结论。** 只能写测试方案或待验证假设。

## 流程

```text
A. 确认是否需要 case 测试
B. 确认测试目标
C. 生成候选场景池
D. 用户选择/删除/补充场景
E. 生成 case 草案
F. 用户确认/修改/替换 case
G. 提供记录模板选项
H. 用户人工测试并回填材料
I. 基于材料编码、聚类、抽象策略维度
J. 将结果补充进报告
```

## A：确认是否需要 case 测试

先说明适用性，再让用户决定。

```text
如果只是做公开资料、功能和口碑调研，可以跳过 case 测试。
如果需要比较真实回答策略、验证公开口碑或为 prompt/产品优化找依据，建议进入 case 测试模块。
```

## B：确认测试目标

至少确认：

| 项目 | 示例 |
|---|---|
| 测试目的 | 回答策略对比、真实体验验证、prompt 优化依据 |
| 竞品范围 | 豆包、千问、ChatGPT、小爱 |
| 场景范围 | 搜索、决策建议、陪伴、车载、办公 |
| case 数量 | 每类 2-3 个、总计 10 个以内等 |
| 颗粒度 | 快速观察、标准对比、深度记录 |
| 是否包含自家产品 | 是/否 |
| 是否加入已知失败 case | 是/否 |
| 测试环境 | App、Web、车端、语音、会员/免费 |

## C：生成候选场景池

先给场景池，而不是直接给最终 case。

默认先输出候选场景池和每类 1 个示例 case，不要一次性生成完整 10-12 个测试集。只有当用户明确要求“给完整草案”“直接生成一版测试表”“先给我一套完整 case”时，才输出完整 case 列表。

示例：

| 场景类型 | 适合观察什么 |
|---|---|
| 信息搜索 / 事实问答 | 时效性、来源、搜索整合、准确性 |
| 决策建议 | 需求判断、对比框架、推荐逻辑 |
| 生活服务 | 实用性、步骤清晰度、场景贴合 |
| 情绪陪伴 | 情绪识别、共情、边界、安全 |
| 工作效率 | 任务拆解、格式交付、可编辑性 |
| 学习辅导 | 解释层次、引导、难度适配 |
| 创作生成 | 风格控制、结构、可用度 |
| 多轮任务 | 上下文保持、约束遵循、修正能力 |
| 语音/车端 | 短句表达、安全边界、行动闭环 |
| 多模态 | 图片理解、文件理解、跨模态推理 |
| 自定义业务场景 | 用户提供的真实业务问题 |

让用户选择：

```text
请确认这次要测哪些场景。可以保留、删除、补充，也可以替换成你的业务真实问题。
```

## D/E：生成 case 草案

case 输出必须标注为“草案”。

模板：

```markdown
## Case 测试集草案

### 场景一：{{场景名}}

- Case 1：{{问题}}
  - 观察目标：{{观察目标}}
  - 适用产品：{{产品范围}}
  - 注意事项：{{测试入口/模式/限制}}

- Case 2：{{问题}}
  - 观察目标：{{观察目标}}

请确认：
1. 哪些 case 保留？
2. 哪些 case 删除？
3. 哪些 case 要替换成你的业务真实问题？
4. 是否加入自家产品已知失败 case？
5. 每类场景数量是否合适？
```

## F：用户确认后再进入记录模板

在用户确认 case 前，不要把测试集当作最终版。

如果用户直接要求“给我表格”，仍应说明：

```text
下面是记录模板草案；case 和字段都可以改，建议先确认后再执行测试。
```

## G：记录模板选项

### 轻量版

适合快速竞品观察、截图+备注。

| Case | 产品 | 回答截图/原文 | 亮点 | 问题 | 备注 |
|---|---|---|---|---|---|

### 标准版

适合后续策略归纳。

| Case | 产品 | 回答摘要 | 结构表现 | 信息质量 | 交互/引导 | 亮点 | 问题 | 证据 |
|---|---|---|---|---|---|---|---|---|

### 深度版

适合正式报告或策略矩阵。

| Case | 产品 | 原始回答 | 任务完成度 | 需求判断 | 信息组织 | 表达风格 | 工具调用 | 多轮表现 | 用户感受 | 策略判断 | 证据 |
|---|---|---|---|---|---|---|---|---|---|---|---|

### 自定义版

当用户已有记录表或内部标注标准时，优先适配用户现有结构。

## H：用户回填材料要求

建议用户回填：

- 测试产品；
- 测试入口和模式；
- 是否会员/登录；
- 原始问题；
- 原始回答或截图；
- 多轮过程；
- 用户主观备注；
- 测试日期；
- 异常情况。

如果材料不完整，先标注限制，不要强行下结论。

## I：从回填材料抽象策略维度

使用类似用户研究的流程：

```text
熟悉材料
→ 给每条回答/交互打观察标签
→ 聚类成候选策略主题
→ 检查每个主题是否有足够证据
→ 命名和定义策略维度
→ 生成策略矩阵
```

### 观察标签示例

标签应来自材料，以下仅作参考：

| 类别 | 示例标签 |
|---|---|
| 需求判断 | 主动澄清、默认假设、直接回答 |
| 信息组织 | 结论前置、分层结构、大段文字、重点标记 |
| 任务完成 | 给步骤、给决策框架、只解释不落地 |
| 交互引导 | 尾部追问、下一步建议、无引导 |
| 工具调用 | 联网搜索、引用来源、图片/文件工具、无工具 |
| 表达风格 | 简洁、啰嗦、亲和、正式、模板化 |
| 安全边界 | 风险提醒、拒答、替代建议、过度保守 |
| 多轮表现 | 记住约束、丢失上下文、能修正、重复 |

## J：输出策略分析

模板：

| 策略维度 | 产品 A | 产品 B | 产品 C | 自家产品 | 证据 case | 启示 |
|---|---|---|---|---|---|---|

结论卡：

```text
事实依据：哪些 case / 回答材料支持？
观察：不同产品表现出什么模式？
判断：这说明什么策略差异？
建议-取长（竞品已验证，要跟上）：
建议-补短（竞品共同没做好，有机会超越）：
建议-避坑（竞品失败/收缩路径，要规避）：
限制：样本数量、测试环境、随机性、版本限制是什么？
```

## 禁止事项

- 不要直接给最终测试集并让用户照填。
- 不要把 case 草案写成最终方案。
- 不要在没有回填材料时生成策略矩阵。
- 不要把单次输出差异当作稳定产品差异。
- 不要忽略测试环境差异，例如会员/免费、App/Web、模型模式、是否联网。
- 不要为了表格完整而编造用户未测试的产品表现。
