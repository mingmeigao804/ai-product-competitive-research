# 公开体验反馈与用户口碑分析（可选章节）

该文件用于分析公开渠道中的用户体验反馈。**本节为可选**：用户在范围确认时提供了知乎/微博/小红书社媒材料（链接/截图/评论文本）才写口碑章节；没提供就整节省略，不凑应用商店评分，不写缺口占位。

这里的"体验"指市场一般用户在社媒平台表达出来的真实评价、讨论和截图，不等同于研究者亲自测试产品。

**口碑材料只认社媒真实评价 + 截图。** 来源是知乎、微博、小红书、B站、酷安等社媒平台上的用户原话、讨论帖、截图。**应用商店评分是聚合数字，没有分析意义，不作为口碑来源**（iTunes 评分仅可用于功能现状佐证，不进入口碑章节）。

## 社媒材料获取（curl 抓不到，必须向用户索要）

知乎/微博/小红书/B站反爬强，curl 在本环境抓不到真实评论全文（已验证）。因此口碑材料**必须由用户提供**：

- 范围确认阶段询问用户是否有知乎/微博/小红书口碑材料（链接/截图/评论文本）。
- 用户提供的材料可以是：URL（skill 尝试 curl 直读，能读就读）、截图（用户贴）、直接粘贴的评论文本。
- 用户未提供社媒材料时，**口碑章节整节省略**，不写、不凑评分、不写缺口。

## 核心原则

1. **社媒真实评价是口碑的唯一材料。** 知乎/微博/小红书/B站/酷安的用户原话、讨论、截图。
2. **不用应用商店评分做口碑。** 评分是聚合数字，无分析意义；iTunes 评分仅可佐证功能现状。
3. **真实材料先于结论。** 没有社媒材料时不输出口碑结论，输出缺口。
4. **不要把单条评论当作普遍结论。** 高频、多来源、跨平台重复出现的反馈才更适合上升为结论。
5. **保留用户原话和截图。** 原话能体现真实语言、情绪和场景；截图作为证据附在过程文件。
6. **标注样本偏差。** 小红书、知乎、微博、B站、酷安的用户群体和表达方式不同。
7. **标注置信度。** 对证据强弱保持透明。

## 常见信息源

| 来源 | 适合观察什么 | 注意事项 |
|---|---|---|
| 小红书 | 使用场景、种草/吐槽、截图、生活化表达 | 样本偏年轻化，内容可能偏种草 |
| 微博 | 热点传播、品牌声量、事件反馈 | 容易受热点影响，情绪波动大 |
| 知乎 | 长文评价、理性分析、对比讨论 | 用户偏深度表达，不一定代表大众 |
| B站 | 视频演示、评论区反馈、真实使用过程 | 关注评论与弹幕中的体验表达 |
| App Store / 应用商店 | 评分、稳定性、会员、功能问题 | 负面反馈可能集中于 bug 和付费 |
| 酷安 | 技术用户反馈、安卓体验、功能细节 | 样本偏极客，要求可能更高 |
| 产品社区 | 核心用户需求、功能建议、长期问题 | 可能偏重度用户 |
| 媒体评测 | 功能解读、行业定位、横向对比 | 需要区分媒体判断和用户反馈 |
| 用户截图/公开视频 | 入口、界面、交互路径、实际呈现 | 截图可能来自特定版本或灰度 |

## 分析流程

使用“材料 → 编码 → 主题 → 发现”的方式，不要直接从零散评论跳到结论。

```text
收集公开材料
→ 提取原始反馈
→ 给每条反馈打标签
→ 聚类成体验主题
→ 判断主题证据强弱
→ 输出用户感知和产品启示
```

## Step 1：整理原始反馈

先按产品和来源整理材料。

| 产品 | 来源 | 原始反馈/截图摘要 | 时间 | 链接/证据 | 备注 |
|---|---|---|---|---|---|

要求：

- 尽量保留用户原话，不要过早改写。
- 如果是截图或视频，摘要说明画面中的功能、入口、用户操作和评论。
- 如果时间敏感，记录日期。

## Step 2：编码标签

对每条反馈标注体验标签。标签应来自材料，不要强行套固定框架。

常见标签：

| 标签类别 | 示例标签 |
|---|---|
| 功能可见性 | 入口明显、功能难找、命名不清 |
| 使用门槛 | 操作复杂、学习成本低、路径太长 |
| 结果质量 | 回答清楚、幻觉、信息过时、推荐有用 |
| 效率价值 | 省时间、减少搜索、替代人工整理 |
| 情绪价值 | 陪伴感、会安慰、像真人、有趣 |
| 表达体验 | 啰嗦、结构清楚、重点突出、太正式 |
| 稳定性 | 卡顿、失败、崩溃、响应慢 |
| 价格/会员 | 太贵、限制多、免费够用、权益不清 |
| 差异化感知 | 比竞品强、没有记忆点、像某产品 |
| 使用场景 | 学习、办公、搜索、陪伴、娱乐、车载 |
| 信任问题 | 不敢信、来源不清、专业场景风险 |

## Step 3：聚类成体验主题

把相近标签合并成主题。主题应能回答“用户为什么在意这个点”。

示例：

| 体验主题 | 包含标签 | 说明 |
|---|---|---|
| 功能露出有效 | 入口明显、用户主动截图、功能被反复提到 | 用户能感知到功能存在 |
| 回答结构降低理解成本 | 结构清楚、重点突出、适合学习 | 用户觉得信息组织有帮助 |
| 功能多但学习成本高 | 功能难找、入口分散、设置复杂 | 产品能力强但不易被普通用户使用 |
| 情绪价值形成差异化 | 像真人、会安慰、有陪伴感 | 用户将产品当成陪伴对象 |
| 可靠性削弱信任 | 幻觉、过时、无来源、不敢信 | 用户不敢在关键任务中使用 |

## Step 4：判断置信度和样本偏差

### 置信度

| 置信度 | 标准 |
|---|---|
| 高 | 多平台、多用户、多条材料重复出现，且有截图/原话支持 |
| 中 | 同一平台或有限材料中反复出现，有一定证据但覆盖不足 |
| 低 | 个别评论、单一截图、来源不明或仅为推测 |

### 样本偏差

常见偏差：

- 平台人群偏差：小红书偏生活分享，酷安偏极客，知乎偏深度讨论。
- 情绪偏差：应用商店负面反馈更容易来自 bug 或付费不满。
- 传播偏差：热门帖子可能放大极端体验。
- 版本偏差：截图和评论可能来自旧版本、灰度版本或地区限定版本。
- 付费偏差：会员能力和免费能力可能不同。

输出时写清：

```text
该主题置信度：高/中/低
证据来源：
可能样本偏差：
是否需要进一步验证：
```

## Step 5：形成公开体验反馈矩阵

| 产品 | 高频场景 | 正向反馈主题 | 负向反馈主题 | 典型用户原话 | 置信度 | 样本偏差 | 启示（取长/补短/避坑） |
|---|---|---|---|---|---|---|---|

## Step 6：提炼用户感知定位

用户感知定位不是官方定位，而是公开反馈中体现出来的用户心智。

示例：

```text
产品 A：用户更常把它当作学习/办公助手。
产品 B：用户更常把它当作陪伴和娱乐场景工具。
产品 C：用户更常把它当作搜索增强工具。
```

分析时说明依据：

- 哪些场景被反复提到；
- 哪些功能被用户截图和传播；
- 用户用什么词形容产品；
- 正负反馈集中在哪里。

## 写作注意

- 写“公开反馈显示/用户评论中反复出现”，不要写“用户真实体验一定是”。
- 如果证据来自单一平台，明确说明。
- 如果没有足够证据，不要为了完整性补结论。
- 用户原话可以短，但要保留语气和关键信息。
- 分析要上升到体验主题和产品启示，不要只堆评论。
