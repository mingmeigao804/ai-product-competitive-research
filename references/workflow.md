# AI 产品竞品调研主流程

该文件定义标准公开资料调研主线。按用户问题的复杂度裁剪流程：轻量问题只执行相关步骤，完整竞品调研才执行全流程。

## 总览

先判断执行模式：

- **框架模式**：只输出调研框架、方法、模板或 case 测试设计，可以不联网。
- **报告/调研执行模式**：用户要生成报告、完成调研、整理近期动作、分析功能现状或口碑，必须先执行真实联网检索或读取用户提供的最新材料。
- **case 深挖模式**：用户要真实回答策略对比或交互测试，进入可选 case 测试模块。

报告/调研执行模式的标准流程：

```text
阶段 0：确认调研目标与边界
阶段 1：生成调研方案与检索计划
阶段 2：真实联网检索与来源表整理
阶段 3：近期动作整理与产品功能矩阵
阶段 4：公开体验反馈与用户口碑分析
阶段 5：趋势、差异化与机会点总结
阶段 6：生成 Markdown / 飞书报告
可选：深度 case 测试模块
```

真实检索细则见 `source-research-playbook.md`。

## 阶段 0：确认调研目标与边界（一次性，全程唯一人工确认点）

### 目标

一次性把 6 项必备信息问清，**不分多次、不挤牙膏**。用户回复后自动跑到底，中途不再确认。

### 一次性输出范围确认块

用户提出竞品调研需求后，**立刻**输出下面这个块。已从用户原话里能读到的字段直接预填，读不到的留空让用户补。**不要先问一两个、再问一两个**——一次出齐：

```text
请一次性确认/补全以下 6 项（已根据你的话预填，错的改、缺的补）。回复后我自动跑到底，中途不再打断你确认。

1. 调研主题：{{哪类 AI 产品/功能}}
2. 调研目标：{{要支持什么决策/产出什么}}
3. 调研主体（主要竞品）：{{要调研的竞品列表}}
4. 对标主体：{{自家产品，检索不到可空缺，不脑补}}
5. 时间范围：{{近期动作的时间窗}}
6. 目标产物：{{飞书文档 / Markdown / 汇报提纲}}

已有材料（可选）：
- 官方/媒体链接：
- 知乎/微博/小红书口碑材料（链接/截图/评论文本）：{{提供了才写口碑章节；不提供就不写该节，不凑应用商店评分}}
```


### 硬停：等用户回复这一条

输出范围确认块后**停下，等用户回复**。这是全程唯一的人工确认点。不要在用户回复前开始检索或生成。

### 用户回复后

把 `research-state.md` 的 `范围已确认` 置为 yes，`当前阶段` 置为 `阶段0`，跑 `node scripts/research-gate.js scope`。通过后**自动跑完阶段 1→6，不再逐段停下等确认**（来源门禁未通过时输出缺口报告停下，那是硬停不是确认）。门禁输出向用户可见，但不需要用户回复才继续。

在进入阶段 1 前，执行 30 秒通道快速探测：对百度、Bing、一个官方博客 sitemap、iTunes Search API 各发一条 curl，标记当前环境 ✅/❌ 通道，写入 `research-state.md` 的 `检索进度.已检索平台`。探测结果决定后续检索策略（哪些通道可用、是否需要用户补料）。探测命令见 `references/sources-registry.md` 末尾"新环境通道快速探测"。

## 阶段 1：生成调研方案与检索计划

### 目标

把调研拆成可执行步骤，明确资料来源、中间产物和真实检索计划。报告/调研执行模式下，调研方案必须包含检索计划；不能只给报告大纲。

### 输出结构

```markdown
## 调研方案

### 1. 调研目标

### 2. 竞品范围
- 直接竞品：
- 间接替代：
- 用户现有习惯 / workaround：

### 3. 分析维度
- 近期动作
- 产品功能
- 公开用户体验反馈
- 竞品定位与差异化
- 待验证问题

### 4. 检索计划
- 官方资料：
- 更新日志/官方博客：
- 帮助中心/文档：
- 应用商店：
- 场景化/垂域运营功能（iTunes Search API）：{{中文产品（豆包/千问/元宝/Kimi/DeepSeek）且时间范围含近 3 个月时必查；海外产品可跳过}}
- 媒体报道：
- 社媒/社区：
- 用户已有材料：
- 每个竞品无法覆盖的来源：

### 5. 阶段产物
- 竞品动作表
- 功能矩阵
- 公开体验反馈矩阵
- 机会点总结
- 最终报告 + 过程文件
```

方案与检索计划写入过程 markdown 文件，向用户展示一句"按此方案执行"，**不停下等确认**，直接进入阶段 2。

## 阶段 2：真实联网检索与来源表整理

### 目标

对竞品执行真实联网检索或读取用户提供的最新材料，建立来源表。AI 产品竞品调研的时效性很重要；报告/调研执行模式下，不能跳过该阶段。

完整规则见 `source-research-playbook.md`。

### 硬门禁：来源检查

检索后、写报告正文前，必须跑 `node scripts/research-gate.js sources`。脚本读取 `source-table.md`，按竞品统计来源数与类型数，对照 `research-state.md` 中的阈值（默认每竞品 ≥3 来源、≥2 类型，中文竞品常因第 3 类来源难获取下调；海外竞品通常可达 3/3，需更严时显式 `--min-types 3`）。

- **未通过 → 只输出缺口报告（见 `references/gap-report.md`），停下。** 不写报告正文、近期动作结论、功能现状或口碑结论，不用"启示/建议/规划方向"凑篇幅。把门禁输出向用户可见，说明哪个竞品缺哪类来源。
- 通过 → 输出来源覆盖小结（写入过程文件），**不再停下等用户确认**，直接进入阶段 3。

### 来源优先级

| 来源 | 适合验证什么 |
|---|---|
| 官网 / 产品页 | 功能事实、产品定位 |
| 官方博客 / 更新日志 | 近期版本、模型/功能发布 |
| 发布会 / 开发者文档 | 能力边界、技术方向 |
| 媒体报道 | 背景解释、行业评价 |
| 应用商店更新说明 | App 层功能变化 |
| 社媒/社区 | 用户感知、传播点 |
| 用户提供材料 | 内部背景、自家产品情况、已收集证据 |

### 分类方式

| 类型 | 示例 |
|---|---|
| 模型层 | 新模型、推理能力、搜索整合、长上下文、多模态 |
| 应用层 | App 新入口、新模式、交互变化、工具整合 |
| 功能层 | 深度研究、语音、图片、文件、记忆、Agent |
| 运营层 | 活动、会员权益、生态合作 |
| 商业化 | 定价、订阅、企业版、API 策略 |
| 市场传播 | 主打卖点、品牌定位、用户心智 |

### 来源表模板

| 竞品 | 信息点 | 类型 | 来源标题 | URL | 发布时间/访问时间 | 可信度 | 摘要 | 用于章节 |
|---|---|---|---|---|---|---|---|---|

### 写作要求

- 先建立来源表，再写近期动作、功能矩阵和口碑结论。
- 每条近期动作必须有来源和时间；没有来源或时间的信息不得进入近期动作表。
- 对时效性敏感的信息标注日期。
- 对来源不明确的信息标注“待验证”。
- 不把营销话术直接当作能力事实。
- 在尚未收集资料前，不要把产品定位、优势、短板写成结论；应标注为“待验证假设”或“后续验证方向”。

## 阶段 2.5：近期动作整理

### 目标

从来源表中整理竞品在指定时间范围内的公开动作，并判断其与本次调研主题的关系。

| 竞品 | 动作 | 类型 | 时间 | 来源 | 对本次主题的影响 | 待验证点 |
|---|---|---|---|---|---|---|

## 阶段 3：产品功能矩阵

### 目标

将不同竞品的产品能力和功能设计放在同一张矩阵中比较。

### 维度生成方式

根据调研主题动态生成维度，不使用固定表。

示例：

| 主题 | 可能功能维度 |
|---|---|
| AI 搜索 | 联网搜索、来源引用、深度研究、多轮追问、搜索结果整合、回答模式 |
| AI 陪伴 | 人设创建、长期记忆、主动消息、语音通话、角色社区、安全边界 |
| AI Agent | 任务规划、工具调用、过程透明、异常恢复、用户控制、结果交付 |
| AI 办公 | 文件理解、PPT/表格生成、协作编辑、知识库、模板、导出格式 |
| 车载 AI | 语音入口、车控能力、导航/出行、短句表达、安全边界、场景感知 |

### 表格模板

| 功能维度 | 产品 A | 产品 B | 产品 C | 自家产品 | 证据来源 | 备注 |
|---|---|---|---|---|---|---|

单元格建议使用：

- `支持：形态/入口/限制`
- `不支持`
- `公开资料不明确`
- `需人工验证`

### 注意

- 功能矩阵主要比较“是否有、怎么做、用户是否能感知到”。
- 不在功能矩阵中直接评价真实体验质量，除非有公开反馈或测试材料支持。

## 阶段 4：公开体验反馈与用户口碑分析

详细方法见 `public-feedback-analysis.md`。

### 目标

分析市场一般用户如何感知各产品的功能、体验和定位。

### 核心区分

公开体验反馈 ≠ 亲自真实测试。

公开体验反馈来自用户评论、社媒截图、应用商店、社区讨论、媒体评测等材料，反映的是市场感知和用户表达。真实产品体验需要人工测试或用户提供测试材料。

### 输出

- 正向体验主题
- 负向体验主题
- 高频使用场景
- 用户感知定位
- 典型用户原话
- 样本偏差
- 置信度
- 待验证点

## 阶段 5：趋势、差异化与机会点总结

### 目标

把事实和公开反馈转成对产品决策有用的结论。

### 建议结构

```markdown
## 趋势与机会点

### 行业共识

### 竞品分化

### 用户感知

### 自家产品机会

- 取长（竞品已验证，要跟上）：
- 补短（竞品共同没做好，有机会超越）：
- 避坑（竞品失败/收缩/争议路径，要规避）：

### 风险与反方证据

### 待验证问题
```

### 竞争边界扩展

不要只看直接竞品。必要时补充：

| 类型 | 说明 |
|---|---|
| 直接竞品 | 同类 AI 产品 |
| 间接替代 | 搜索引擎、内容社区、垂类 App、办公软件 |
| 用户现有习惯 | 自己搜索、问朋友、看小红书/知乎、打开原生 App |
| 手工 workaround | 复制粘贴、多工具拼接、人工整理 |
| no decision | 用户放弃、忍受、继续原流程 |

### 结论要求

每个核心结论尽量回答：

```text
事实依据是什么？
公开观察是什么？
分析判断是什么？
对自家产品有什么启示？
还需要验证什么？
```

## 阶段 6：生成 Markdown / 飞书报告

报告模板见 `report-templates.md`；飞书落地见 `feishu-report-writing.md`。

### 强制：目标产物=飞书文档时必须写入飞书

**目标产物若是飞书文档，必须调 `doc_create` + `doc_append` 把 5 节正文写入飞书，不许停在本地 markdown 就交差。** 真实跑里出现过只产出本地 markdown 没建飞书文档的失败，此处为硬规则。

流程：5 节正文齐备 → `doc_create` 建文档（title=报告标题）→ 按节 `doc_append` 追加 → 把飞书链接返回给用户。`blocks_added` 字段常返回 0 但实际写入成功，不要当失败。过程内容（来源表/检索记录/缺口/结论卡五字段）写本地过程 markdown，不进飞书。

环境无 feishu-mcp-pro 时退回 Markdown，并明确告知用户"未写入飞书（无 MCP）"。

### 写入验证

每次 `doc_append` 后，调 `doc_fetch`（scope=outline）验证刚写入的章节标题是否出现在文档大纲中。若不在，重试一次 `doc_append`；两次均失败则告知用户"第 X 节可能未写入成功，请手动检查飞书文档"。不要仅凭 `blocks_added`（常返回 0）判断写入是否成功。

### 生成前必含章节检查（强制）

报告正文必须包含以下 4 节，**任一缺失不得生成报告**：

1. 背景与目标
2. 近期动作总览（行业动态——这是重点之一）
3. 策略对比（功能矩阵 + 策略维度矩阵——这是重点之一）
4. 总结（含场景矩阵或机会点）

**功能体验与用户口碑是可选章节**：用户在范围确认时提供了知乎/微博/小红书社媒材料（链接/截图/评论文本）才写该节；没提供就不写，不凑应用商店评分，不写缺口占位。

不得只交"近期动作表"就当成完整报告。某节无来源支撑时，格子写"公开资料不明确/需人工验证"，但章节不省略（口碑除外，口碑可整节省略）。

### 对标主体处理

对标主体（自家产品）是检索对象之一，但**不是报告重心**。检索不到时：

- 功能矩阵/策略矩阵中对应列留空或写"公开资料不明确"；
- 不脑补"对自家产品的启示""规划方向"；
- 报告重心放在行业动态与竞品差异化上。

### 其他生成前检查

- 来源门禁是否已通过（`node scripts/research-gate.js sources` 输出 GATE PASSED）？未通过则不得生成正文，只能输出缺口报告。
- 是否包含 case 测试结果？如果没有，不要写成已测试结论。

### 报告风格

- 正文干净、可交付，不要"一眼 AI"：不堆"事实依据/公开观察/分析判断"五字段、不写"本报告基于…"式元说明。
- 用一句话结论 callout + 表格/矩阵承载信息。
- 结论回到行业趋势与差异化，而非空泛的"竞品很好"。
- 过程性内容一律放过程 markdown，不进正文。

## 是否进入可选 case 测试

在阶段 5 后或用户明确提出时，判断是否需要进入 case 测试。

进入条件：

- 用户需要比较真实回答策略。
- 用户需要验证公开口碑是否符合实际体验。
- 用户需要为 prompt 或产品策略优化收集证据。
- 用户明确要求设计 case 测试。

不进入条件：

- 用户只需要市场动态、功能调研、公开口碑或汇报材料。
- 用户没有时间或材料做真实测试。
- 公开资料已经足够支持当前决策。

进入后读取 `optional-case-testing.md`。
